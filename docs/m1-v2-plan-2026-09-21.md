# PAGe M1/M2 Redesign Plan — 2026-09-21

## Status

This document defines the redesign direction before implementation. It intentionally treats the current M1 alignment/template machinery as a frozen comparator, not as the architecture to incrementally patch.

New development branch/worktree:

- branch: `agent/m1-v2-from-first-principles`
- worktree: `PAGe-m1-v2`
- base commit: `fd6a4e59437936550220d8c048046c8a361f9778`

The existing working tree is intentionally untouched because it contains unrelated M2/manuscript/research changes.

---

# 1. Product objective

From an epidemiologist's perspective, PAGe should answer only the operational questions that matter in real time.

After weekF (week 8):

1. Has the seasonal epidemic started?

Once ignition is detected, at every weekly origin:

2. When will the epidemic peak occur?
3. What will the observed percentage be at `t + 1`?
4. What will the observed percentage be at `t + 2`?

The internal M0/M1/M2 decomposition exists to support those outputs. It is not itself a user-facing product requirement.

Primary operating window:

- ignition through peak;
- peak + 1 week;
- peak + 2 weeks.

Once peak passage is confirmed, exact late-season percentage prediction is lower priority. M1 should stop emitting a user-facing future peak forecast after peak passage, although internal phase/curve state may continue to support M2.

---

# 2. Conceptual decomposition

## M0 — ignition detection

Purpose:

- determine causally whether the seasonal epidemic has started;
- activate the forecasting episode;
- provide the first timing landmark for M1 and M2.

M0 should be judged against expert decimal ignition labels, but its runtime declaration is necessarily discrete because data arrive weekly.

Keep distinct:

- `ignition_truth_decimal`: latent expert-labelled ignition time;
- `ignition_detect_origin`: first weekly origin at which the causal algorithm declares ignition.

M1 and M2 begin operational forecasting at `ignition_detect_origin`, not at the latent decimal truth.

## M1 — peak timing only

Purpose:

- estimate the continuous peak time;
- quantify uncertainty in that estimate;
- update the estimate sequentially as new weekly observations arrive;
- determine when the peak has been reached/passed;
- stop exposing a future peak forecast once passage is confirmed;
- optionally maintain internal phase/shape state for M2 after peak passage.

Primary latent target:

`T_peak* in R`

Example output before passage:

- point estimate: week 27.2;
- uncertainty interval or full distribution over decimal peak time.

Uncertainty should generally contract as informative observations accumulate. Non-monotone local changes may occur when new evidence genuinely conflicts with prior beliefs, but persistent erratic widening/jumping is undesirable.

## M2 — numeric forecasting only

Purpose:

Forecast the observed epidemic percentage at exactly:

- `t + 1`;
- `t + 2`.

M2 may use:

- all causally available observed history;
- M0 ignition information;
- M1 peak-time estimate/distribution;
- peak-relative common-curve features;
- ignition-relative features;
- calendar information;
- other causally available covariates.

M2 should not be responsible for determining the official peak timing.

# 3. Reference truth: expert decimal annotation

The weekly observed maximum is not assumed to be the true epidemic peak. Weekly aggregation obscures the latent continuous timing of ignition and peak.

Therefore, reference timing should be expert-labelled directly in decimal epidemiological week.

For each of all 11 historical seasons, record:

- `season`;
- `ignition_week_decimal`;
- `peak_week_decimal`;
- `annotator`;
- `annotation_version`;
- `timestamp`;
- optional `comment`.

Derived quantity:

`duration_ignition_to_peak = peak_week_decimal - ignition_week_decimal`

## Annotation API

Create a small interactive Plotly-based annotation interface.

Proposed API shape:

```r
labelSeasonTiming(data, season, labels = NULL)
```

Behavior:

- show the complete weekly seasonal curve;
- clearly display epidemiological week on the x-axis;
- optionally mark weekF;
- display current ignition and peak labels if available;
- allow approximate click/drag placement if convenient;
- require explicit numeric decimal ignition and peak values;
- overlay vertical markers at entered decimal values;
- require explicit confirmation before saving;
- write a versioned, auditable annotation record.

The numeric values, not screen/pixel coordinates, are authoritative.

Do not silently regenerate labels from an interpolation algorithm.

## Multi-annotator future-proofing

Even if one expert provides the initial labels, store annotations in a format that supports multiple annotators later. Do not overwrite raw labels when creating an adjudicated truth set.

Possible future derived fields:

- adjudicated ignition;
- adjudicated peak;
- inter-annotator disagreement;
- confidence / ambiguity flag.

Inter-annotator variation provides a useful lower bound on practically meaningful model error.

# 4. First analysis before choosing a new model

No M1-v2 statistical model should be selected until the 11-season geometry is characterized.

The first analysis must be descriptive and causal-validation aware.

## 4.1 Ignition-to-peak duration

For all 11 expert-labelled seasons, summarize:

`D_s = T_peak,s - T_ignition,s`

Report:

- all 11 values;
- mean;
- median;
- SD;
- range;
- IQR;
- leave-one-season-out mean/median/prior distribution;
- sensitivity to individual seasons.

Question:

How informative is ignition timing alone about eventual peak timing?

This is expected to be a strong baseline and may already account for a large fraction of M1 performance.

## 4.2 Ignition-aligned trajectories

Align all seasons at expert decimal ignition.

Inspect the interval:

- ignition;
- first 1 week after ignition;
- first 2 weeks after ignition;
- through peak + 2.

Questions:

- how similar are early post-ignition levels and increments?
- how quickly do trajectories separate?
- how much information about time-to-peak appears after 1 and 2 post-ignition observations?
- are there obvious outlier seasons?

Do not rely on an edge derivative as the principal feature. Boundary slope estimation is noisy and was previously abandoned for good reason. Use the observed local trajectory directly or stable summaries of it.

## 4.3 Peak-aligned trajectories

Align historical seasons at expert decimal peak.

Focus on the operational interval from typical ignition timing through peak + 2.

Questions:

- how much common shape is actually present?
- how variable is amplitude?
- how variable is width?
- how asymmetric are rise and early decline?
- is a single low-dimensional common curve adequate?
- are a few low-rank deviations sufficient?

The late decline should not drive model complexity because it is not a primary product target.

## 4.4 Information accumulation by origin

At each causal origin after ignition, ask how much additional information exists about `T_peak*` beyond the ignition-derived prior.

Origins of special interest:

- ignition detection origin;
- +1 observed week;
- +2 observed weeks;
- subsequent weekly origins through peak passage.

Compare:

- ignition-only prior;
- prior + current level/history;
- prior + one post-ignition observation;
- prior + two post-ignition observations;
- richer trajectory models.

The purpose is to learn what the data can actually identify before selecting model complexity.

# 5. M1-v2 modeling principles

## 5.1 Directly estimate peak time

M1-v1 indirectly estimated peak time through template alignment parameters such as phase shift and dilation.

M1-v2 should parameterize the primary target directly:

`T_peak*`

Avoid introducing latent transformations whose only purpose is to recover peak time afterward.

## 5.2 Ignition provides the initial timing prior

At ignition detection, initialize a causal prior over peak time from the outer-training seasons:

`P(T_peak* | ignition information)`

At minimum, this can derive from the LOSO distribution of ignition-to-peak duration.

As new observations arrive, update:

`P(T_peak* | data through origin t)`

The trajectory should update the prior rather than discard it.

## 5.3 Peak-relative historical shape

Historical shape should be represented in coordinates relative to expert-labelled peak:

`r = week - T_peak*`

This separates the known historical peak anchor from shape estimation and removes the need to re-estimate historical peak alignment during common-curve fitting.

The historical shape model should focus on the operational window, especially pre-peak through peak + 2.

## 5.4 Favor low-dimensional historical variation

Current M1-v1 factor-smooth reference models are highly flexible: saved fits with `k_ref = 25` used roughly 169–179 total EDF with 8 training seasons, around 21 EDF per historical season.

This is too much freedom to assume necessary for a peak-timing problem without direct evidence.

Candidate representations to evaluate conceptually/empirically:

1. one strongly regularized canonical peak-relative curve;
2. canonical curve + low-rank season deviations;
3. functional PCA / low-rank basis of peak-relative trajectories;
4. hierarchical probabilistic shape model.

The chosen representation should use the minimum complexity required to improve LOSO peak inference and M2 short-horizon forecasting.

## 5.5 Do not automatically restore free dilation

The old `tau`/`delta` parameterization showed weak identifiability on partial rising trajectories.

Initial M1-v2 should not include freely optimized dilation/width unless evidence shows that pre-peak data can identify it and that it improves LOSO peak timing.

If width variation is needed, prefer a strongly regularized/hierarchical distribution and integrate over uncertainty rather than freely optimizing width independently at each origin.

## 5.6 Positive amplitude only

If amplitude scaling is required, parameterize it so positivity is guaranteed, for example:

`b = exp(beta)`

Do not estimate under a positive constraint and later overwrite the fitted scale with an unconstrained recalculation.

Amplitude should be regularized around historically plausible values.

## 5.7 Uncertainty is a first-class output

M1 should maintain a distribution or well-defined approximation over peak time, not only a rounded best week.

The model must be able to say that the peak is not yet tightly identified.

Desired behavior:

- broadest near ignition;
- generally narrower after informative observations;
- sufficiently narrow before/near the peak in ordinary seasons;
- wider in genuinely atypical seasons;
- stable enough that small observation noise does not cause multi-week oscillation.

# 6. M1 public and internal contracts

## 6.1 Public output before peak passage

At each origin after ignition and before passage confirmation:

- decimal peak point estimate;
- uncertainty interval and/or quantiles;
- optional probability that peak occurs within next 1/2/3 weeks.

The public product should not expose internal template IDs, phase parameters, optimizer states, etc.

## 6.2 Public output after peak passage

Once peak passage is confirmed:

- stop forecasting a future peak date;
- expose a simple status such as `peak_reached_or_passed`;
- optionally report the locked peak estimate if useful.

## 6.3 Internal state after peak passage

M1 may continue to provide M2 with:

- locked decimal peak estimate;
- peak-relative phase;
- common-curve expected level at `t+1` and `t+2`;
- curve uncertainty summaries;
- confidence/passage state.

This internal support can continue even though the user-facing peak question is finished.

---

# 7. Peak passage / confirmation

Peak forecasting and peak confirmation are different tasks and should remain separate internally.

M1-F:

- forecast/infer future or current peak timing.

M1-C:

- determine whether enough causal evidence exists to say the primary peak has been reached/passed;
- lock the operational peak state;
- stop public future-peak output.

Candidate evidence may include:

- posterior mass for peak lying at/before current time;
- recent observations relative to recent maximum;
- sustained evidence of decline;
- persistence across multiple origins.

The exact rule must be designed and validated separately. It should not simply inherit the old `peak_passed` logic.

Secondary-peak handling must be explicit. The default operational assumption should likely be that once the primary peak is confirmed and locked, later bumps do not reopen the original peak forecast unless a pre-specified exceptional rule exists.

# 8. M2 interface and use of the common curve

M2 forecasts only `t+1` and `t+2`.

M1 and M2 run concurrently from ignition detection onward.

M1 does not need to know the true current-season peak before M2 can use peak-relative shape information.

Before peak lock, M1 can provide M2 with a posterior-averaged common-curve predictor.

If `g(r)` is the peak-relative common curve and `P_t(T_peak*)` is the current M1 belief:

`E[g(t+h-T_peak*) | data_t]`

for `h = 1, 2` can be used as an M2 feature or offset-like baseline.

M1 may also provide uncertainty summaries such as:

- variance of expected curve level;
- lower/upper quantiles;
- probability of crossing peak before each horizon.

After peak lock, the peak-relative baseline becomes effectively anchored to the locked peak.

## Common curve role

The common curve is not itself the final M2 forecast.

It is a biologically/epidemiologically informed seasonal baseline or predictor.

M2 learns the numeric correction from that baseline using only causally available information.

# 9. Validation design

All model development and evaluation must remain season-level outer LOSO.

The 11 origins/seasons are the independent units for outer validation. Weekly origins within a season are repeated measurements, not independent samples.

No held-out season's expert peak or ignition truth may enter runtime features for that season.

Historical expert truth may be used only in the outer-training seasons to fit timing priors and shape models.

## 9.1 M1 primary metrics

Evaluate only after causal ignition detection and until peak passage.

Primary timing metrics:

- decimal peak MAE;
- median absolute error;
- fraction within +/-0.5 week;
- fraction within +/-1 week;
- fraction with error >=2 weeks;
- signed error by season and origin.

A 2-week error should be treated as operationally large, not merely acceptable noise.

## 9.2 M1 probabilistic metrics

Evaluate:

- interval coverage;
- interval width;
- proper scoring rule for peak-time distribution if practical;
- calibration of probabilities such as peak within next 1/2/3 weeks;
- uncertainty width as a function of weeks since ignition;
- excessive week-to-week posterior movement.

Do not demand mechanically monotonic interval shrinkage if new observations legitimately introduce uncertainty, but characterize and penalize pathological oscillation.

## 9.3 Peak-passage metrics

Evaluate:

- false early confirmation;
- confirmation delay;
- locked peak accuracy;
- post-lock invariance;
- inappropriate reopening/reversion.

## 9.4 M2 primary metrics

Evaluate separately at:

- horizon +1;
- horizon +2.

Stratify by phase:

- early after ignition;
- approaching peak;
- peak week;
- peak +1/+2;
- post-peak if still operationally evaluated.

Primary numeric metrics can include MAE and calibration/coverage if M2 is probabilistic.

Late decline performance should not dominate model selection.

## 9.5 End-to-end system validation

For every held-out season and every weekly origin:

1. reveal only data available through that origin;
2. run M0 causally;
3. if not ignited, do not activate M1/M2 seasonal forecasting;
4. once ignited, initialize/update M1 using only causal information;
5. generate M1 state and common-curve features;
6. forecast M2 `t+1` and `t+2`;
7. update weekly until/after peak passage according to the operational contract.

Do not feed test-season truth-aligned curves into M2 at early origins.

# 10. Required baselines

Before sophisticated models, establish simple LOSO baselines.

## M1 baselines

1. ignition-only mean duration:
   `T_peak_hat = ignition + mean_LOSO(D)`
2. ignition-only median duration;
3. empirical LOSO distribution of `D`;
4. simple updates using current level/recent observations if justified.

Any complex M1-v2 model must materially outperform these simple epidemiologically plausible baselines.

## M2 baselines

At minimum compare against:

1. persistence / last observation;
2. simple local change model;
3. common-curve-only forecast conditional on M1 state;
4. current frozen production comparator where appropriate.

# 11. Legacy M1-v1 policy

The sealed comparator remains frozen.

Do not mutate:

`results/releases/m1-release-v1.0.0`

Legacy M1-v1 findings remain useful as evidence about failure modes:

- reproducibility achieved;
- primary integer MAE about 1.156 weeks under the sealed contract;
- large season-specific failures;
- little global directional bias;
- weak template-ranking signal;
- optimizer max-evaluation frequency;
- severe parameter/template instability;
- unconstrained post-fit negative scale bug;
- unclear/insufficient peak-passage semantics;
- incomplete serialization for causal decomposition;
- highly flexible factor-smooth historical templates;
- poor identifiability of alignment/dilation on partial trajectories.

These findings motivate the redesign but do not dictate the new implementation.

Avoid carrying over old `tau`, `delta`, template softmax, or independent-origin refitting merely for compatibility.

# 12. Sequential state requirements

The new runtime should have explicit state.

At minimum, after ignition:

```text
season_id
origin_week
ignition_detect_origin
ignition_truth_decimal       # evaluation only, never runtime in held-out season
peak_posterior_state
peak_point_estimate
peak_interval
peak_passage_state
locked_peak_decimal
common_curve_features_h1
common_curve_features_h2
uncertainty_features
model_version
```

Every weekly transition should be serializable and reproducible.

The model should not rely on reconstructing hidden optimizer state after the fact.

# 14. Implementation phases

## Phase 0 — protect current work

Already established:

- use separate clean worktree/branch;
- do not touch the dirty legacy checkout;
- do not modify sealed v1 release.

## Phase 1 — expert truth tooling

Deliver:

- Plotly season annotation API;
- versioned annotation schema;
- validation rules (`peak > ignition`, plausible decimal ranges, season identity);
- export/load helpers;
- tests for deterministic storage and update behavior.

Stop and obtain expert labels for all 11 seasons before statistical redesign proceeds.

## Phase 2 — descriptive epidemiological geometry

Deliver a reproducible report containing:

- all 11 annotated curves;
- ignition-aligned panel;
- peak-aligned panel;
- ignition-to-peak duration distribution;
- early post-ignition trajectory summaries;
- between-season peak-relative shape variability;
- low-rank/fPCA diagnostics if useful;
- simple LOSO timing-prior performance.

Decision gate:

Determine how much model complexity is justified.

## Phase 3 — minimal M1 baseline

Implement a transparent sequential baseline:

- LOSO ignition-to-peak prior;
- decimal peak distribution;
- weekly causal update mechanism using minimal trajectory information;
- no free dilation initially;
- no legacy template softmax;
- explicit posterior/uncertainty output.

Compare against the frozen v1 comparator using the new expert decimal truth where applicable.

Decision gate:

Only add complexity if a clearly diagnosed error mode remains and the added parameter is identifiable.

## Phase 4 — historical shape model

Fit/select the minimum adequate peak-relative representation.

Candidates:

- canonical smooth;
- canonical + low-rank deviations;
- functional PCA;
- hierarchical probabilistic curve.

Use outer LOSO only for performance claims.

Integrate shape evidence into M1 peak-time updating.

## Phase 5 — peak-passage state machine

Implement and validate M1-C independently.

Requirements:

- causal;
- persistent state;
- explicit lock;
- false-confirmation control;
- no silent reversion;
- explicit secondary-peak policy.

## Phase 6 — M1-to-M2 interface

Freeze a small, documented interface before M2 redesign.

Candidate fields:

```text
peak_mean_or_median
peak_sd_or_interval_width
prob_peak_within_1w
prob_peak_within_2w
prob_peak_passed
curve_mean_h1
curve_mean_h2
curve_sd_h1
curve_sd_h2
locked_peak_if_any
```

Avoid exposing large opaque latent vectors unless evidence shows they improve M2.

## Phase 7 — M2 redesign

Build M2 specifically for +1/+2 forecasts.

Start simple.

Compare:

- no M1 features;
- point peak feature only;
- common-curve features;
- common-curve + M1 uncertainty;
- richer causal covariates only if justified.

M2 complexity must earn itself under outer LOSO.

## Phase 8 — end-to-end release candidate

Run complete causal walk-forward LOSO across all 11 seasons.

Produce:

- user-facing output ledger;
- M1 peak forecast ledger;
- peak-passage ledger;
- M2 +1/+2 forecast ledger;
- uncertainty/calibration diagnostics;
- season-level failure analysis;
- frozen release manifest.

1. Keep the old working tree untouched.
2. Implement only the expert decimal annotation tooling on the new branch.
3. Obtain ignition and peak labels for all 11 seasons.
4. Freeze/version the first expert annotation set.
5. Run the descriptive ignition-aligned and peak-aligned analysis.
